# S1 FAQ / AI 协作规则

> 用途：复制到具体 Stage 后，沉淀 AI 高频反复追问的问题，以及跨需求可复用的默认规则。

## 文档内容范围、结构与格式约定（必读）

### 1. 本文档负责什么

本文档用于沉淀 AI 在当前 Stage 中高频反复追问的问题，以及跨需求可复用的默认规则。

本文档只负责：

1. 记录跨需求共用的默认约定。
2. 记录 AI 容易重复确认的口径、优先级、判断规则与记录方式。
3. 降低后续对话中的重复澄清成本。

本文档不负责：

1. 记录某个单独需求的特殊讨论。
2. 记录完整聊天过程。
3. 替代需求文档中的验收、测试、 bug 修复记录。
4. 替代 [bugs.md](bugs.md) 记录跨需求 bug / 中断条目。

### 2. 本文档固定结构

本文档必须长期保持以下结构：

1. 文档内容范围、结构与格式约定
2. 使用规则
3. FAQ 条目
4. 新增条目模板
5. 更新日志

### 3. 本文档记录格式

每个 FAQ 条目使用以下固定格式：

- `FAQ-ID`：唯一编号，例如 `S1-FAQ-001`
- `问题`：AI 反复会问的真实问题
- `默认答案`：当前默认执行口径
- `适用范围`：影响哪些需求或整个 Stage
- `何时改写`：出现什么条件时需要更新本条

## 使用规则

1. 只有“会跨需求复用”或“AI 已多次重复追问”的问题，才写入 FAQ。
2. 单需求特殊规则写回对应需求文档，不写 FAQ。
3. bug 条目、打断开发的临时问题、未归属缺陷优先写入 [bugs.md](bugs.md)，而不是 FAQ。
4. FAQ 一旦形成默认口径，后续执行优先按 FAQ 处理，除非需求文档明确覆盖。
5. 若 FAQ 与单需求文档冲突：
   - 单需求内的局部特殊口径，以单需求文档为准；
   - 跨需求通用规则，以 FAQ 为准。

## FAQ 条目

### S1-FAQ-001：当前 Stage 文档体系应该如何使用？

- `问题`：当前 Stage 文档到底看哪些？更新时先改哪里？
- `默认答案`：
  1. 先看 [README.md](README.md) 了解总体目标与优先级。
  2. 再看 [requirements-index.md](requirements-index.md) 找到目标需求。
  3. 进入对应需求文档处理该需求的全部细节。
  4. 若形成跨需求规则，再更新本文档。
- `适用范围`：整个 Stage
- `何时改写`：文档结构再次调整时。

### S1-FAQ-002：是否需要记录每轮对话原文？

- `问题`：和 AI 的每轮交流要不要逐字记录？
- `默认答案`：不记录原文，只记录有效结果，包括：新需求、需求变更、已确认决策、被否决方案、验收变化、测试结果、 bug 发现与修复结论。
- `适用范围`：整个 Stage
- `何时改写`：若后续引入专门的对话归档系统时。

### S1-FAQ-003：开发过程中突然冒出的 bug 记在哪里？

- `问题`：开发 A 需求时突然发现 B 需求 bug，或者发现一个暂时说不清归属的历史 bug，应该记在哪？
- `默认答案`：先记入 [bugs.md](bugs.md)。如果后续确认它明显属于某个需求，再在对应需求文档补充影响与处理结果，并在 bug 条目里回链。
- `适用范围`：整个 Stage
- `何时改写`：bug 管理策略改变时。

### S1-FAQ-004：需求文档应该按时间线写，还是按状态写？

- `问题`：单需求文档到底应该以时间线为主，还是以当前状态为主？
- `默认答案`：采用“状态视图 + 时间线附录”的混合结构。文档前半部分让 AI 快速接手当前状态，后半部分保留工作时间线，记录中断、恢复、测试往返与需求拉扯。
- `适用范围`：整个 Stage
- `何时改写`：需求文档模板变化时。

### S1-FAQ-005：部署是否需要特权容器？

- `问题`：SMB/NFS 后端和虚拟共享是否依赖内核挂载？
- `默认答案`：使用普通容器、host 网络、容器内 root；后端使用 smbprotocol/libnfs 用户态客户端，VFS 通过 Unix socket 访问服务。无 privileged、额外 capability 或 FUSE。NAS 原有 SMB 占用端口时由管理员调整，应用只报告具体冲突。
- `适用范围`：整个 Stage。
- `何时改写`：部署模式变化时。

### S1-FAQ-006：日期、X 和保留天数如何解释？

- `问题`：时区、前导零和不完整录像如何处理？
- `默认答案`：文件名与保留策略统一北京时间；X 保留字符串，00 与 0 不合并。保留天数包含当天。只有实际已有录像参与归档，按播放时间 60 倍加速，跨午夜按半开区间切分，归档永久保存。
- `适用范围`：协议、归档、统计。
- `何时改写`：用户修改时间规则时。

### S1-FAQ-007：自动化通过能否视为摄像机验收完成？

- `问题`：如何记录当前验收边界？
- `默认答案`：已通过实际协议及视频处理测试；目标 NAS Docker 构建运行和摄像机实机联调仍待执行，不能写成已通过。已有录像不能直接切换后端地址，第一版无自动迁移。
- `适用范围`：整个 Stage。
- `何时改写`：现场验收有新证据时。

### S1-FAQ-008：PostgreSQL 断线时还能服务吗？

- `问题`：元数据保存在 PostgreSQL，连接故障或故障期间重启如何处理？
- `默认答案`：用户在 2026-10-09 明确只需内存缓存。配置、索引和队列在 SQLite :memory:，运行中断线继续服务并在重连后同步；冷启动必须从可用的 PostgreSQL 加载。重启允许丢失未同步变更和临时录像，不要求本地持久目录。Samba 运行文件使用 tmpfs，稳定加密密钥由部署环境提供，接入凭据保存 PostgreSQL；归档元数据未确认前保留历史原片。
- `适用范围`：整个 Stage。
- `何时改写`：用户调整离线配置编辑规则，或要求多网关/数据库独立灾难恢复时。
