## 背景与目标

PostgreSQL 持久保存元数据。用户在 2026-10-09 明确：只要求运行中的进程在数据库断线后使用内存缓存持续服务，不要求此时重启恢复；临时录像及未同步的内存变更允许随重启丢失。本条覆盖此前本地持久副本的实现口径。

## 当前口径

1. 配置、设备、目录、录像、归档任务、覆盖关系和会话哈希在 PostgreSQL 保存；启动从一致性数据库快照加载，重建内存索引和虚拟目录。
2. SQLite :memory: 用于内存索引及按记录合并的事务队列，temp_store=MEMORY；不生成数据库、WAL 或本地密钥文件。
3. 运行期间数据库断线，摄像机与管理操作继续使用内存，配置可编辑，恢复连接后自动同步。队列与未同步变更随进程结束丢失。
4. 重启要求 PostgreSQL 可用，只恢复数据库已保存的配置及远程录像，临时缓存和工作视频会丢弃，未保存的元数据不会恢复。
5. Samba 运行文件、凭据库、目录占位及转码清单放在 tmpfs；新增录像及处理视频使用临时 /cache，不要求任何本地持久目录。
6. 存储密码及摄像机密码加密后写 PostgreSQL，用部署环境中的稳定 CAMMON_SECRET_KEY 解密。启动重建 Samba 凭据，原用户名/密码可继续登录；密钥不写本地文件。
7. 元数据同步按修订号和主键幂等提交，远端提交后确认内存队列，新修订不被旧确认清除。依赖记录与摄像机凭据随批次一起提交，任何已提交批次可加载。
8. 删除历史原片之前，还须等对应归档、任务及全部日期覆盖关系在 PostgreSQL 确认。断线时原片保留，避免重启丢失归档的内存状态导致历史数据不可恢复。
9. 每个 schema 一个活跃写入会话；数据库锁阻止并发覆盖。运行期间不会回读外部手工数据库改动；同一进程可从内存重新同步较旧快照，冷启动完全采用数据库。

## 功能拆解 / 实施拆解

1. database.py：纯内存索引、事务队列、修订号、条件确认、依赖闭包及启动快照导入。
2. metadata.py：启动读取 PostgreSQL、独立线程提交、断线重试、schema 锁和冲突保护。
3. security.py、core.py、samba.py：内存密钥、加密凭据入库、Samba 临时认证重建与缓存清理。
4. archive.py：RAM 转码清单，归档元数据确认后才能删除历史原片。
5. Compose、Dockerfile、前端、README 和测试：取消 /data 与缓存持久卷，使用 tmpfs 与临时视频目录，展示正确的内存服务边界。

## 验收标准

1. 启动从 PostgreSQL 恢复配置、元数据、字符串 X、文件大小及设备接入凭据；不会用空内存索引覆盖数据库。
2. 真实 PostgreSQL 断线期间配置编辑、随机写入、读回和视频转存继续成功，连接恢复后同步一致。
3. 元数据数据库与密钥不产生任何本地文件，队列仅在进程内存中；进程重启丢弃临时录像及未同步配置。
4. PostgreSQL 不可用时冷启动明确失败，不能宣称支持断线重启恢复。
5. 事务失败、确认丢失、并发修改和数据库锁等待不丢当前进程变更、不重复记录、不阻塞摄像机全局锁。
6. 批次含关联父记录、任务清单和凭据，冷启动可通过内存索引的外键校验。
7. 完全清空运行目录后，真实 SMB1 客户端使用原用户名和密码成功认证并读取已有后端录像。
8. 元数据库断线后发布归档、丢失内存并重启，旧原片仍保留且可重新处理；PG 确认归档后才删除原片。
9. 页面准确显示仅内存运行、断线状态和待同步数量；Compose 无本地持久卷；连接及密钥不通过 API 暴露。
